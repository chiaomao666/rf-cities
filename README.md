# rf-cities

主要頁面：`city_query_site.html`，獨立據點戰監測站。只顯示收到據點戰標記的城市，
原本的一般城市主權列表已移除，資料庫內容不刪除。
優先依 `sword` 判斷；舊版上傳資料則解析 `nation_battle` JSON 的活動 ID／報到時間，
或使用據點戰比分。空值、無法解析的戰況與明確結束的戰鬥不列出。
若採集端沒有上傳最新結束訊號，本站仍可能看到過期戰況，不能保證與遊戲完全同步。

## 本機預覽與部署

直接開啟 `city_query_site.html` 即可預覽。部署至 GitHub Pages 後，使用
`/rf-cities/city_query_site.html` 開啟；此次修改尚未推送或部署。
`city_infiltration_site.html` 保留未改動。

## 持續更新

- 使用既有 Supabase `cities` 表格與公開讀取金鑰。
- 啟用 `cities` 的 Supabase Realtime / Postgres Changes 後，收到事件立即同步。
- 未連上即時訂閱時，每秒自動補查；失敗則逐步延長重試，最多 30 秒。
- 即時訂閱正常時，每 60 秒完整補查，避免漏失事件。
- 分頁讀取全部城市，搜尋與排序在更新後保留；變動的列短暫以黃色標示。
- 「最新城市資料時間」取資料列的 `updated_at`；「同步於」僅代表本站成功讀取資料庫。

資料庫需允許公開角色讀取 `cities`，但不應為了網站開放不受限制的寫入。
切勿把 service-role 金鑰或遊戲登入憑證放進網頁或 GitHub。

## 尚待接入的戰況資料

此版本持續更新交戰城市列表，不代表已完成攻守戰力監測。
現有遊戲端 `city_uploader.js` 有上傳節流，且將 `nation_battle` 轉為文字；
網站更新速度不能突破遊戲端的上傳頻率。
要顯示完整戰況，接下來需讓採集端保留結構化戰況、城市 ID、活動 ID、
攻守戰力與人數、來源時間及明確的結束訊號，再加入本站戰況視圖。
報到倒數截止不是戰鬥結束；未取得的戰力也不能顯示成 0。
獨立網站本身無法讀取玩家瀏覽器的遊戲狀態，也不會繞過遊戲參戰資格。

## 遊戲端據點戰採集（已接入）

遊戲資料夾 `2.28/assets/mods/city_battle_uploader.js` 已於 `assets/index.html`
安排在主程式之前載入。更新後必須重新整理遊戲，舊連線不會自動附加監聽器。

採集器被動讀取既有 WebSocket 收到的 `cities` 增量資料，並以 RFStore 補初始狀態。
變動約 200 毫秒後批次上傳，結束訊號同樣上傳；活動未變動時每 30 秒維持一次上傳。
上傳失敗保留佇列並退避重試。遊戲內「據點戰資料上傳」面板顯示收到封包與成功上傳數。
瀏覽器除錯時也可使用 `RFCityBattleUploader.getStatus()` 查看狀態。

沿用 `cities.nation_battle` text 欄位儲存 JSON，無需新增欄位：
活動 ID、報到截止時間及 `_rf_monitor` 的 active、score、observed_at、source。
僅上傳城市 ID、戰況與 updated_at，不上傳完整封包、帳號憑證或完整城市資料。
網站以 `_rf_monitor.active` 決定是否列出城市。原城市上傳器不再寫入此欄位，避免覆蓋。

Supabase 必須允許目前採集器憑證對 `cities` upsert；若收到 401／403，需先設定適當的
採集身分與寫入政策，不要改成公開任意寫入或把 service-role 金鑰放進腳本。
本機測試已驗證採集與重試，未以虛構戰況写入線上資料庫；實際上傳仍需遊戲接收新封包。
遊戲必須保持開啟並登入；沒有收到的戰力數據不能由本站補造。
